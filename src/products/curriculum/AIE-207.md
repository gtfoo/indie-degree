# AIE-207 — Systems for Machine Learning

**3 credits · 60 hours · 5 modules**

> The hardware reality underneath everything above, and the answer to a question the rest of the programme keeps raising without settling: why do modern architectures look the way they do. They look that way because of memory bandwidth. Attention is not slow because of its arithmetic — the arithmetic is cheap — it is slow because it moves more data than it computes on, and once that is a number you have measured rather than a claim you have read, half the design decisions in a modern model stop being arbitrary.

The hardware reality underneath everything above. Explains why architectures look the way they do.

**By the end you can**

- Explain the memory hierarchy of a GPU and why attention is IO-bound
- Profile a training step and identify the bottleneck
- Describe data, tensor and pipeline parallelism and when each applies
- Reason about the arithmetic intensity of an operation

**Sitting rule.** Every item is completable in one sitting. Nothing exceeds 180 minutes, and anything over 90 declares its own checkpoints.

## Modules (28 items)

### M1 — The memory hierarchy, and why attention is IO-bound

*780 minutes*

- **M1.1 · Making deep learning go brrrr, from first principles** — reading, 120 min, tier 0  
[Making Deep Learning Go Brrrr From First Principles](https://horace.io/brrr_intro.html)
- **M1.2 · FlashAttention, for the IO argument** — reading, 150 min, tier 0  
[FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness](https://arxiv.org/abs/2205.14135)
  *Where:* Read this time for the IO-complexity analysis rather than the algorithm. AIE-204 read it as an implementation detail; here the point is the counting of memory accesses that motivates it.
- **M1.3 · Where the time actually goes** — lecture, 165 min, tier 0  
[Stanford CS336 Language Modeling from Scratch I 2025](https://www.youtube.com/playlist?list=PLoROMvodv4rOY23Y0BoGoBGgQ1zmU_MT_) — *Stanford Online*
  *Where:* The GPU and systems lectures — memory hierarchy, kernel launch overhead, and fusion. Cite the course playlist, since the individually reuploaded copies are not authorised.
- **M1.4 · Measure the hierarchy yourself** — assignment, 180 min, tier 1
  Write two microbenchmarks on whatever accelerator you can get free: one that does almost no arithmetic per byte moved, and one that does a great deal. Time both, and convert the timings into achieved memory bandwidth and achieved FLOP/s. Compare each against the device's published numbers. You will not reach either figure, and the size of the shortfall — plus your explanation of it — is the assignment.
  *Checkpoints:* A bandwidth-bound microbenchmark written and timed → A compute-bound microbenchmark written and timed → Achieved bandwidth and achieved FLOP/s computed from the timings → Both compared against the device's published specification
- **M1.5 · Attention's IO cost, from your own numbers** — assignment, 150 min, tier 2
  Count, on paper, how many bytes a naive attention implementation moves and how many floating-point operations it performs, for a stated sequence length and head dimension. Take the ratio. Compare it against the bandwidth-to-compute ratio you measured in M1.4 and predict whether attention is memory-bound or compute-bound at that shape. Then time it and see whether your prediction held. Do this at two sequence lengths, because the answer changes with length and that is the whole point.
  *Checkpoints:* Bytes moved by a naive attention implementation counted analytically → FLOPs counted analytically for the same shapes → The ratio computed and compared against the device's ratio from M1.4 → The prediction checked against a timed run
- **M1.6 · Retention: the memory hierarchy and its costs** — retention, 15 min, tier 1

### M2 — Arithmetic intensity and the roofline

*720 minutes*

- **M2.1 · Performance, from the course that builds it** — reading, 180 min, tier 0  
[stanford-cs336/spring2025-lectures](https://github.com/stanford-cs336/spring2025-lectures)
  *Where:* The lecture notes and accompanying code on GPU performance and arithmetic intensity.
- **M2.2 · Four operations, predicted then measured** — assignment, 180 min, tier 1
  Take four operations — an elementwise activation, a layer normalisation, a small matrix multiply and a large one. Derive the arithmetic intensity of each by hand: operations per byte moved. Predict which are memory-bound and which are compute-bound, and write the predictions down before running anything. Then measure. Report how many you got right, including the ones you did not, because a wrong prediction traced to its cause teaches more than four correct ones.
  *Checkpoints:* Arithmetic intensity derived by hand for four operations → A bound predicted for each, recorded before measuring → All four timed → Predictions scored against outcomes
- **M2.3 · A roofline for the hardware you actually have** — assignment, 165 min, tier 2
  Build a roofline model for your available device using the peaks you measured rather than the ones the vendor advertises. Compute the ridge point — the arithmetic intensity above which you become compute-bound. Plot the operations from the previous assignment. Then use the plot to argue for one specific optimisation on one specific operation, and say what you expect it to buy before trying it.
  *Checkpoints:* Peak bandwidth and peak compute established empirically, not from the datasheet → The ridge point computed → The four operations from M2.2 plotted on it → One operation's position used to argue for a specific optimisation
- **M2.4 · Kernels, from naive to fused** — reading, 180 min, tier 0  
[karpathy/llm.c](https://github.com/karpathy/llm.c)
  *Where:* The CUDA kernels under dev/cuda — read the progression from the naive version to the optimised one for a single operation, and the comments explaining each step.
- **M2.5 · Retention: arithmetic intensity and the roofline** — retention, 15 min, tier 1

### M3 — Profiling a real training step

*720 minutes*

- **M3.1 · Making the training step fast, with the measurements** — lecture, 180 min, tier 0  
[Let's reproduce GPT-2 (124M)](https://www.youtube.com/watch?v=l8pRSuU81PU) — *Andrej Karpathy*
  *Where:* The optimisation sections — precision, fused kernels and compilation, each justified by a measurement rather than by reputation.
- **M3.2 · The profiler, and a real regression** — reading, 165 min, tier 0  
[pytorch/pytorch](https://github.com/pytorch/pytorch)
  *Where:* The profiler documentation, plus one issue thread about a genuine performance regression — read for how the diagnosis was actually reached.
- **M3.3 · Attribute every millisecond of a training step** — assignment, 180 min, tier 1
  Profile one training step of the model you built in AIE-204. Attribute the time: forward, backward, optimiser, data loading, and whatever is left. Break the largest contributor down to individual kernels. Report the unattributed remainder explicitly — profilers never account for everything, and a breakdown that sums to exactly 100% has been rounded into agreement.
  *Checkpoints:* A single training step profiled with a real profiler → Time attributed to forward, backward, optimiser and data loading → Kernel-level breakdown for the largest contributor → Unattributed time reported rather than absorbed
- **M3.4 · One change, predicted before it is made** — assignment, 180 min, tier 2
  Pick one optimisation the profile actually justifies — mixed precision, a fused optimiser, compilation, a larger batch — and predict the speedup quantitatively before making the change. Then make it and re-profile. Compare the prediction against the outcome. Getting the number wrong is expected; not being able to say why afterwards is the failure, and a prediction made after the measurement is not a prediction.
  *Checkpoints:* One optimisation chosen from the profile and the reason recorded → A quantitative prediction written down before the change → The change made and re-profiled → Prediction and outcome compared, with any gap explained
- **M3.5 · Retention: profiling and attribution** — retention, 15 min, tier 1

- **M4.2 · Switch Transformers, for the routing cost** — reading, 120 min, tier 0  
[Switch Transformers: Scaling to Trillion Parameter Models with Simple and Efficient Sparsity](https://arxiv.org/abs/2101.03961)
- **M4.3 · Communication volume, by hand** — assignment, 180 min, tier 1
  Fix a model size and a cluster shape — eight devices, a stated parameter count, a stated batch. Derive how many bytes cross the interconnect per training step under data parallelism, under tensor parallelism, and under pipeline parallelism. Divide by a realistic interconnect bandwidth to get a time. You cannot run this, and you do not need to: the arithmetic is the deliverable, and it is what the strategy choice actually rests on.
  *Checkpoints:* A model size and cluster shape stated → Bytes communicated per step derived for data parallelism → The same for tensor and for pipeline parallelism → The three compared against a stated interconnect bandwidth
- **M4.4 · Choose a strategy for a stated budget** — assignment, 165 min, tier 2
  Given a concrete scenario — a model that does not fit on one device, a fixed number of GPUs, a budget and a deadline — choose a parallelism strategy or combination and defend it with your own communication arithmetic rather than by citing what a large lab did. Then state what would change your answer: a different interconnect, a different model shape, a smaller batch. A recommendation with no stated failure conditions is an opinion.
  *Checkpoints:* A concrete scenario fixed — model size, hardware, budget, deadline → A strategy or combination chosen → The choice defended with the arithmetic from M4.3 → The conditions that would flip the decision stated

### M5 — Apply it to something you actually run

*660 minutes*

- **M5.1 · The systems view of your own inference path** — assignment, 180 min, tier 2
  Take an inference path from one of your own products and describe it in the terms of this course: for each stage, is it bound by memory, by compute, or by the network between you and the provider. Reconcile that against the cost and latency numbers AIE-105 produced from the outside. The deliverable is one optimisation that only becomes visible from the systems view — and it is a legitimate outcome to conclude that for an API-backed product, the answer is that none of it is yours to optimise.
  *Checkpoints:* One of your own products' inference paths described in systems terms → The bound identified for each stage — memory, compute, or network → AIE-105's cost and latency measurements reconciled with this view → One optimisation identified that the outside view could not see
- **M5.2 · Publish the performance chapter** — project, 180 min, tier 3
  Publish a chapter covering what you measured and what it changed. Include a prediction you got wrong — they are the most instructive part of a performance write-up and the first thing most authors delete. It must connect backwards: AIE-105 measured cost from outside the model, AIE-204 built the thing being measured, and this chapter is what joins them.
  *Checkpoints:* Written for a reader who has never profiled anything → The roofline and the profile both included and explained → At least one prediction that was wrong, kept in → Published and connected backwards to AIE-105 or AIE-204
- **M5.3 · Where the systems view changes an architecture choice** — assignment, 120 min, tier 2
  Pick a feature of modern architectures whose real motivation is hardware rather than modelling — grouped-query attention, the shape of a feed-forward layer, the choice of head dimension. Reconstruct the systems argument for it from your own measurements. Then state what would have to be true about a device for that feature to stop being worth it. This is the outcome the course exists for: architectures look the way they do because of the machines they run on, and being able to say which parts are which is rare.
  *Checkpoints:* An architectural feature identified whose motivation is systems, not modelling → The memory or bandwidth argument for it reconstructed → What it would cost on a device with a different ratio, stated
- **M5.4 · Oral defense** — defense, 60 min, tier 4
